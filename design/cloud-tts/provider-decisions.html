朗读服务选型记录

2026-09-28，2026-09-29 更新 · 记录每家朗读服务为什么考虑、为什么用或不用。数字全部来自 scripts/speech-bench.sh 实测（说明见 Tools/SpeechBench/README.md），除非标明「文档」。

结论：目前只有阿里 Qwen-Audio 同时满足三条硬要求，作为第一个接入的云端朗读员。系统语音保留。豆包、CosyVoice、Gemini、OpenAI 暂不启用，代码保留（豆包、CosyVoice、Gemini 的适配代码在 Sources/Core/Speech/Engines/，在 TTSEngineRegistry.paused 里标为暂停）。ElevenLabs 已测（2026-09-29）：流式和逐字时间都满足，但首音 1.2–2.4 秒、价格约为 Qwen 的 5 倍，暂不采用。MiniMax 等 key。

一、硬要求（不满足就不开启）

#要求怎么判定
1流式输出服务一边合成一边发音频，收到第一段就能播，不用等整段合成完。
2足够快「实际首音」（按下到听见声音，包括为了不卡顿需要多攒的缓冲）≤ 800 毫秒；并且首包之后等 300 毫秒开播，全程不断。
3实时字幕每个字（词）的时间要在它被念出来之前到手，才能逐字高亮。「一句念完才给」「整段合成完才给」都不算。判定：字的时间覆盖原文 ≥ 90%，且没有「念过了时间才到」的字。

不满足的宁愿先不开启，不做「凑合能用」的版本。

三、每家的细节

阿里 Qwen-Audio：采用

  • 字的时间怎么来的：它每发一段音频，前面都跟一条消息，里面是「这一句到目前为止已合成的字和时间」，列表越来越长。第一个字的时间和第一段音频相差 0–5 毫秒。官方文档只写了句末那条消息带时间，是抓包才发现的（2026-09-28）。
  • 先给的时间会不会被改：对比每句最后的完整列表，改动 0 毫秒，可以直接用。
  • 必须按句一条条发：整段一次发过去时，长的英文段落有时要整段合成完才给时间（实测晚 1.8 秒）。按句发就没这个问题。
  • 实测（英文和中英混排 7 段 × 3 次）：实际首音 290–460 ms，合成速度 RTF 约 0.1（比念快 10 倍），全程不卡，字 100% 对上原文（数字「2024」念成「二零二四」也能对上）。
  • 小问题：以引号开头的英文句（"We're not there yet,"），第一个字的时间晚到约 0.2–0.4 秒，而且时间是均匀间隔的，看起来像估算值。
  • 协议：阿里百炼 WebSocket（run-task / continue-task / finish-task），key 用百炼的 API Key（sk- 开头），和 QDuo「AI 模型」页里通义千问用的是同一种 key。

豆包：暂停

为什么考虑：中文自然度公认最好，国内 AI 应用大量在用；你点名要。

为什么不用：字幕不是实时的。HTTP 和 WebSocket 双向两种接口都实测过，行为一样：一个分句的音频全部发完之后，字幕才到。

 110 ms  WebSocket 连接建立
 142 ms  会话开始
 589 ms  第一段音频（开始出声）
 …       连续 20 段音频，没有任何字幕
1959 ms  字幕（事件 364）：「打开 Xcode 的 Build Settings，把 Swift Language Version 改成 Swift 6，」
2198 ms  字幕：「然后 clean build 一下就好了。」

官方双向接口文档（volcengine.com/docs/6561/1329505，2.0 音色）也这么写：「在一句音频合成之后，不会立即返回该句的字幕……当一句的字幕识别完成后立即返回。可能一个子句的字幕返回的时候，已经返回下一句的音频帧给调用方了。」字幕里每个字带「可信度」数值，推测是合成后再识别出来的时间，所以必然比音频晚（推测，未证实）。

开头落后多少：首包后 0.6–1.6 秒才有第一条字幕，第一句开头最多落后约 1.2 秒；从第二句起正常。

试过但没用的办法：

  • 换 WebSocket 双向接口：字幕时机不变，首音反而慢 150–250 ms（每次要多建连接、开会话两个来回）。
  • 把第一句切短分开发：没用，豆包会把文字合起来，再按自己的规则断句。

什么情况下重新考虑：豆包推出随音频实时返回的字幕；或者我们接受「开头先估算高亮，字幕到了再校正」的做法。

代码：VolcengineEngine.swift（HTTP）、VolcengineBidirectional.swift（WebSocket 双向，二进制协议已实现并实测可用）。你配置文件里豆包的 key 没动。

ElevenLabs：暂不采用

为什么考虑：国际上知名度最高，音色库最大；接口按字符给时间，对中文正好一个字一个时间。

实测（2026-09-29，模型 eleven_v3，预置音色 Sarah，9 段测试文字 × 2 次，接口 /v1/text-to-speech/{voice}/stream/with-timestamps，PCM 24 kHz）：

项目结果
流式返回是。音频一段段发回，每段一条 JSON
逐字时间是。每段音频自带这段每个字符的开始、结束时间，和音频同时到；9 段文字 100% 对上原文（中文、数字、中英混排都对上）
跟得上实时基本是。合成速度 RTF 0.5–0.8（比念快 1.2–2 倍，明显比 Qwen 的 0.1 慢）；英文新闻句那段按 300 毫秒缓冲会卡一次
首音1.2–2.4 秒（热连接 1.2–2.0 秒），远超 800 毫秒的要求

慢在哪：网络不是主因（TCP 2 毫秒；TLS 约 0.4 秒，走出国线路）。连接复用后，服务器仍要约 0.9 秒才回响应头、约 1.2 秒才给第一段音频。eleven_v3 是主打音质的模型；主打速度的 eleven_flash_v2_5（官方称模型延迟约 75 毫秒）没有测。

价格（官方 API 价格页，2026-09-28 调研时记录，今天未重新核对）：

模型每百万字符折合每万字（按 1 美元 ≈ 7.1 元）
eleven_v3约 $80约 ¥5.7
eleven_flash_v2_5约 $40约 ¥2.8
对比：阿里 Qwen-Audio flash约 ¥100约 ¥1

免费账号的限制（实测）：每月 1 万字符；不能通过接口使用音色库里的音色（报 402「paid_plan_required」），只能用账号自带的预置音色。

结论：满足流式和逐字时间，但首音不达标，而且 v3 的价格约是 Qwen 的 5–6 倍，用不起。暂不采用，代码保留（ElevenLabsEngine.swift）。

什么情况下重新考虑：测 eleven_flash_v2_5 的首音能进 800 毫秒，且价格能接受。

阿里 CosyVoice：暂停

为什么考虑：文档明确支持逐字时间；和 Qwen-Audio 同一个 key、同一套协议，接入成本几乎为零；最便宜。

为什么不用：① 你试听后觉得效果一般；② 字的时间来得晚：首包后 0.9–2.6 秒，第一句切短也还落后最多约 2 秒；③ 合成速度只比念快约 3 倍，21 组里有 1 组出现过卡顿。

Google Gemini TTS：暂停

为什么考虑：盲听排行榜第 2，便宜。

为什么不用：Gemini API、Live API、Google Cloud TTS（包括 Chirp 3 HD 和云上的 Gemini 音色）都没有自动的逐字时间（2026-09-28 查文档）。不满足硬要求 3。

OpenAI：不做

接口不返回任何时间信息。不满足硬要求 3。没有写适配代码。

调研阶段就排除的

  • 阿里 qwen3-tts-flash-realtime：和 Qwen-Audio 是两条产品线，用于语音对话，文档里没有逐字时间。
  • Deepgram、Hume：不支持中文。
  • Amazon Polly：只有一个中文音色，逐字时间要另发一次请求。
  • Cartesia、Inworld、Azure、腾讯云、讯飞：没有进入第一批，没有测。

四、怎么重新启用一家

把它从 Sources/Core/Speech/TTSEngineRegistry.swift 的 paused 列表里删掉，在测速配置 ~/.config/qduo/speech-bench.json 里加回它那一段（模板见 Tools/SpeechBench/Template.swift 的历史版本），重新跑 scripts/speech-bench.sh run。

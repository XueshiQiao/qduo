一句话方案：在 QDuo 里加一层「朗读引擎」接口，第一批接 豆包（火山引擎）、MiniMax、ElevenLabs、OpenAI 四家；每家只需写一个「适配文件」，把它自己的请求方式翻译成统一的「一段段音频 + 每个字的时间」。播放器边收边播（流式），拿到时间信息的就逐字高亮，拿不到的按句高亮。系统语音保留，作为没配 key、断网、出错时的兜底。设置页根据每家的「配置项清单」自动生成，以后加一家不用改界面代码。

名词说明：TTS = 文字转语音；流式 = 服务器一边合成一边往回发，我们收到第一小段就开始播，不用等整段合成完；时间戳 = 服务器告诉我们「第几个字从第几毫秒开始念」，逐字高亮全靠它；PCM = 没压缩的原始音频数据，拿到就能直接播，不用解码。

二、现在 QDuo 的朗读

整个朗读就是 Sources/PopBar/Actions/Speaker.swift 一个 71 行的类：点「朗读」→ 用系统语音（AVSpeechSynthesizer）按语言挑音色念出来；再点一次停止。没有暂停、没有高亮、没有任何设置项，也没有「引擎」这层抽象。唯一的调用点是 PopBarSession.swift:228，所以替换它影响面很小。

现有可以直接复用的：配置文件 ~/.config/qduo/config.json（ConfigStore，认不出的字段会原样保留）、钥匙串存 key（KeychainStore）、AI 模型页的 key 输入方式。

三、整体结构

为什么系统语音单独一条路，不塞进同一个播放器：系统语音自己会播放、会暂停、耳机切换时自己处理，还自带「念到第几个词」的回调。硬把它的音频掏出来走我们的播放器，要处理每个音色格式不同、部分高级音色吐不出音频等麻烦，得不偿失（Frank 的意见，我同意）。所以最外层是「后端」：系统语音一个，流式一个；朗读条只认后端发出的统一进度，不关心背后是谁。

四、最外层抽象（接口草图）

// 每家厂商一个适配器，只负责「把文字变成一段段 PCM + 时间」
protocol TTSEngine {
    static var descriptor: TTSEngineDescriptor { get }   // 身份证：id、显示名、能力、配置项清单、钥匙串账号
    func synthesize(_ request: TTSRequest) throws -> TTSStream
}

struct TTSRequest {
    let text: String            // 这一块要念的原文
    let model, voice: String
    let speed: Double           // 统一用倍速 1.0；各家自己换算（OpenAI 0.25–4，豆包 −50…100）
    let extra: JSONValue        // 高级参数，原样合并进请求体
    let credentials: [String: String]
}

struct TTSStream {
    let format: TTSAudioFormat                          // 发请求时就定了，如 PCM 24kHz 16bit 单声道
    let events: AsyncThrowingStream<TTSEvent, Error>    // 流结束 = 念完；取消 = 立刻断开网络，不再计费
}

enum TTSEvent {
    case audio(Data)              // 一小块 PCM
    case marks([TextMark])        // 若干个字的时间
}

struct TextMark {
    let range: NSRange            // 对应原文的哪几个字
    let startFrame, endFrame: Int // 从这块音频开头算起的第几个采样点（不用秒，暂停/继续不会漂）
}

struct TTSEngineDescriptor {
    let id: String                // "volcengine" / "elevenlabs" / "minimax" / "openai" / "openai-compatible"
    let displayName: String
    let inputLimit: InputLimit    // 单次上限，单位各家不同：字符 / UTF-8 字节 / token
    let marks: MarkSupport        // .none（按句高亮） / .inline（随音频到） / .trailing（念完一句才到）
    let models: [Option]          // 预置模型列表，另可手填
    let voices: [Option]          // 预置音色列表，另可手填音色 ID（豆包没有「列出音色」的接口）
    let fields: [SettingField]    // 这家额外要的配置项：地区、接口地址……
    let secrets: [SecretField]    // 要哪些 key、存在钥匙串哪个账号
}

这是草图，字段名会在写代码时微调。关键约定：① 音频格式在发请求时就定死，第一批四家都要 PCM 原始音频，不需要解码；② 时间一律换成「原文里的第几个字」+「第几个采样点」，各家格式的差异全部关在适配器里；③ 停止朗读时必须立刻断开网络连接，否则后台还在下载、还在扣钱。

五、流式播放怎么走

  1. 切块：文字没超过这家的单次上限就整段一次发出去（整段念语气最连贯、请求最少）；超了才在句号处切开，每块尽量大。
  2. 预取：正在播第 1 块时，就请求第 2 块；同时最多一个请求在路上，避免撞上 ElevenLabs 低档套餐 2–5 个并发的限制。
  3. 边收边播：收到的 PCM 直接排进 AVAudioEngine 的播放队列。网络包可能把一个采样点切成两半，适配器负责把半截字节留到下一包拼上。
  4. 首音超时：8 秒内没收到第一块音频，就判定失败，改用系统语音念（不是等系统默认的 60 秒）。
  5. 中途出错：已经开始出声后再出错，就停下并在朗读条上报错，不悄悄换成系统语音接着念——念到一半换个声音，比直接报错更让人困惑。
  6. 耳机切换：念的过程中连上 / 断开 AirPods，播放器要重新接上输出设备（系统语音会自己处理，我们的播放器得自己写）。
  7. 字数上限：一次最多念 5000 字（可在设置里改），超出部分不念并在朗读条上说明——防止手滑选了一整篇长文，在 ElevenLabs 上一下花掉几块钱。

六、逐字高亮：各家差异怎么抹平

厂商给的是什么我们怎么处理
ElevenLabs每个字符的开始 / 结束秒数，另有一份「规范化后」的版本（数字被展开成读法）用原文那份，直接对应到字
豆包它自己分好的词 + 起止时间；数字可能被改写（「2024」→「二零二四」）在原文里按顺序模糊查找每个词；对不上的那一句退回按句高亮
MiniMax字幕（流式时如何返回，未证实）第一版按句高亮，实测拿得到再升级
OpenAI / 兼容接口不给时间按句高亮：知道哪一块正在播，就高亮那一块

另一个坑：网页里复制来的文字常带零宽字符、多余空格。清理可以，但必须保留「清理后第几个字 ↔ 原文第几个字」的对照表，否则所有高亮位置都会偏。

七、配置：每家请求方式、参数都不一样怎么办

1. 配置文件长这样（草案）

"speech": {
  "default":    { "engine": "volcengine", "model": "seed-tts-2.0", "voice": "zh_female_vv_uranus_bigtts", "speed": 1.0 },
  "byLanguage": {                                   // 可选：某种语言单独用一套
    "en": { "engine": "elevenlabs", "model": "eleven_flash_v2_5", "voice": "21m00Tcm4TlvDq8ikWAM", "speed": 1.0,
            "extra": { "voice_settings": { "stability": 0.4 } } }   // 高级参数，原样并进请求
  },
  "engines": {                                      // 每家自己的非机密设置
    "minimax":           { "region": "cn" },        // cn = api.minimax.cn，intl = api.minimax.io
    "openai-compatible": { "baseURL": "https://example.com/v1" }
  },
  "maxChars": 5000,
  "fallbackToSystem": true
}

Frank 建议不要做「命名预设 + 路由表」（给每套配置起 id、再用 id 做语言映射），那是多一层间接却没有第二个用处；直接在 byLanguage 里按语言写完整一套就够了。语言在每次朗读开始时判断一次（沿用现在 Speaker.voiceLanguage 的判断），整段用同一个声音，不按句切换——一段话中间换声音听起来像坏了，还会多一次等待。

十一、风险

  • 隐私说法要改：现在代码注释和设置说明写着「朗读不出 Mac」。选了云端引擎后，选中的文字会发给厂商，操作说明和设置页要明确写出来。
  • 时间戳对齐是最容易出细碎问题的地方（数字、英文缩写、标点被厂商改写）。对不上时退回按句高亮，不会念错，只是高亮变粗。
  • 国内外可用性：豆包语音国内账号需实名认证；海外用户要走 BytePlus（国际版，接口地址、价格未证实）。MiniMax 有国内 / 国际两个站，设置里要能切。ElevenLabs、OpenAI 在国内网络可能不通——这时首音超时后会退回系统语音。
  • 费用：由用户自己的 key 付费；字数上限是唯一的保险。
  • 厂商接口会变：各家文档里有的字段本身就没写清（上面标了「未证实」）。第 0 步实测前，接口草图里和时间戳相关的部分都不算定稿。

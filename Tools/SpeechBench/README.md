# speech-bench：云端朗读服务测速

给 QDuo 选朗读服务用的命令行工具。对每家服务真实发请求，测「多久出声」「能不能跟上播放」「逐字高亮能不能用」，并把录音和逐字时间表存下来供人工试听、核对。

各家的接入代码在 `Sources/Core/Speech/`，App 以后直接复用同一套，不是一次性脚本。

## 用法

```bash
scripts/speech-bench.sh init            # 生成 ~/.config/qduo/speech-bench.json（已存在则不动）
# 打开这个文件，填 key，把要测的那家 "enabled" 改成 true
scripts/speech-bench.sh run             # 测所有 enabled 的
scripts/speech-bench.sh run --only volcengine,qwen-audio --text mixed,en-long --repeat 5
```

配置文件里含 key，权限是 600（只有你能读），放在仓库外面，不会被提交。

每次运行的结果在 `build/speech-bench-results/<时间>/`：

| 文件 | 内容 |
|---|---|
| `summary.txt` | 汇总表（终端最后打印的就是它） |
| `runs.json` | 每一次请求的全部数字 |
| `<服务>-<文本>.wav` | 第一次请求收到的录音，可以直接听 |
| `<服务>-<文本>.marks.txt` | 每个字（词）的时间：什么时候收到、第几秒念、服务说的是什么字、对到原文哪个字（对不上会写 ✗ NOT FOUND） |
| `<服务>-<文本>.notes.txt` | 服务返回的原始消息样子（音频数据已替换成长度），排查接口和文档不符时用 |

## 每个数字是什么意思

时间都从「发出请求前一刻」开始算，单位毫秒。

| 名称 | 含义 |
|---|---|
| **conn**（连接） | HTTP：收到响应头；WebSocket：连接建立。包含 DNS、TCP、TLS 握手。`runs.json` 里有分项 `dnsMs / tcpMs / tlsMs` |
| **1st-audio**（首包） | 收到第一段音频的时刻，理论上最早能出声的时间 |
| **1st-mark**（首个字时间） | 收到第一个字的时间信息，最早能开始高亮的时间 |
| **no-stall-start**（无卡顿开播点） | 按每段音频实际到达的时间倒推：最早从什么时候开始播，能保证一路播完不断。算法：对每段音频，取「到达时间 − 它前面已有的音频时长」，全部取最大值 |
| **buffer needed**（需要多攒） | 无卡顿开播点 − 首包时间，即播放器在首包之后还要等多久才敢开播 |
| **effective 1st-sound**（实际首音） | 首包和无卡顿开播点中较晚的那个。**这是用户真正感受到的「按下朗读到听见声音」的时间，汇总表里的 1st-sound 就是它** |
| **total** | 整段音频全部收完 |
| **RTF** | 合成用时 ÷ 音频时长（整次请求）。小于 1 表示合成比念得快 |
| **stream RTF** | 从首包到最后一包的时间 ÷ 音频时长，只看首包之后这段是否比播放快 |
| **realtime ✓/✗**（跟得上实时） | 模拟一个播放器：首包到达后再等 `bufferBudgetMs`（默认 300 ms）开播，缺数据就停下等。一次都没停 = ✓ |
| **marks 覆盖率** | 原文里的字（不算标点和空格）有多少被某个字的时间信息覆盖 |
| **late**（晚到的字） | 按上面的开播时间，某个字的时间信息在这个字已经念出来之后才到，高亮就会落后。个数和最晚多少毫秒 |

## 判定标准（在 `Tools/SpeechBench/Summary.swift` 里，改的话两边一起改）

- **首音**：实际首音中位数 ≤ 800 ms 为 ✓ fast，≤ 1500 ms 为 △ slowish，更慢为 ✗ slow。用预热后的连接算（第一次请求要新建连接，单独列在 cold 一栏）。
- **跟得上实时**：所有次数都 ✓ 才算过。
- **逐字高亮**：覆盖率 ≥ 90% 且没有晚到的字才算过。服务不给时间信息的直接不过：逐字高亮是硬要求。

每组第 1 次请求会先断开所有旧连接（冷启动，相当于 App 刚打开后第一次朗读），后面几次复用连接（热启动）。

## 已接入的服务

| id | 服务 | 协议 | 逐字时间 |
|---|---|---|---|
| `volcengine` | 豆包语音合成 2.0 | WebSocket 双向（默认）；`"transport": "http"` 改走 HTTP 分块 | 有，但每个分句的音频全部发完后才到（两种接口都一样，文档也这么写） |
| `qwen-audio` | 阿里 Qwen-Audio TTS | WebSocket | 文档没说清系统音色有没有，靠实测 |
| `cosyvoice` | 阿里 CosyVoice | WebSocket | 有，但到得晚（首包后 1–2.6 秒）。**已暂停**：试听效果一般，代码保留，工具不再测它 |
| `elevenlabs` | ElevenLabs | HTTP 分块 | 有，逐字符 |
| `minimax` | MiniMax | 双向 WebSocket（`"transport": "http"` 改走 HTTP SSE） | 文档没写逐字时间在哪个字段、何时到，靠实测；前几条非音频消息会原样记进 notes |
| `gemini` | Google Gemini TTS | HTTP SSE | 没有。**已暂停**：代码保留，工具不再测它 |
| `system` | macOS 系统语音 | 本机 | 有，作为基线 |

同一家想比较不同模型，在配置里另起一个名字并写 `"engine"`，例如 `"elevenlabs-v3": {"engine": "elevenlabs", "model": "eleven_v3", …}`。

## Qwen-Audio 的两个开关

Qwen-Audio 是一边发音频、一边发字的时间：每个音频包前面的消息里带着这一句「目前已知的字」，列表越来越长（2026-09-28 抓包确认，官方文档只写了句末那一次）。所以第一个字的时间和第一段音频几乎同时到，早给的时间后来也没有被改过（实测改动 0 毫秒）。

- `splitSentences`（默认开）：按句子一条条发。不开的话，长的英文段落有时会整段合成完才给时间（实测晚 1.8 秒）。
- `pauseMs`（任何服务都可用，默认 0）：每次请求前先等这么多毫秒。MiniMax 新账号每分钟请求数很低，连着测会报 `1002 rate limit exceeded(RPM)`，设成 `4000` 左右就不会撞上。
- `quickStart`（默认关）：把第一句在第一个逗号处再切开。字的时间已经跟着音频来了，不再需要；留着只为对比。

结论先说

  1. Jev 大概率（约八成五把握）是 TypeSafe AI 在 2026-09-15 发布的 Jev 模型：一个只做「判断题 / 选择题」、不生成文字的云端模型，号称 70–500 ms 出答案。它不是一个划词工具。
  2. 语言判断（是不是日文 / 英文）不需要 Jev：苹果自带的 NLLanguageRecognizer 在本机实测每次 0.02–0.2 ms、免费、不联网。Jev 适合的是本地规则写不出来的判断，比如「这段是不是代码」「这是不是一个问题」。
  3. 建议给每个动作加一个可选字段 when：内置语言、文字种类、正则、网址 / 邮箱 / 电话 / 日期 / 地址、文件路径、长度、来源 App 等判断，用 all / any / not 组合。不满足就不显示；判断超时或出错时照常显示（宁可多一个按钮，也不让动作莫名其妙消失）。
  4. 你说的「用 Java 定义判断」应该是 JavaScript。技术上可行：苹果自带 JavaScriptCore，本机实测调用一次不到 1 微秒；难点只在「死循环怎么停」，有办法但要用一个苹果未公开的接口。建议先不做——你举的例子内置判断全都能覆盖，等真有内置写不出来的需求再加。
  5. Jev 不建议用来决定「显示不显示」：它要 70–500 ms，等它回来再往弹出条里加按钮，按钮会在你鼠标移过去的途中跳位置。更合适的用法是点下去之后再问它，比如「翻译」分组里由它挑用哪个子动作。
  6. 分期：第一期内置判断 + 组合 + 编辑界面（约 3–4 天）；Jev 和 JavaScript 各自按需再做（各约 2–3 天）。

1 · 「JJE V / Jev」到底是什么

你口述的是「JJE V」，issue #1 的标题是「Support Jev」，正文为空。我搜了几个方向：

候选查到了什么像不像
TypeSafe AI 的 Jev 模型2026-09-15 发布的「System One」模型。你给它一段内容和几个带类型的问题（是非题 / 选择题 / 打分题），它返回带概率的答案，不生成任何文字。官方说 70–500 ms，输入 $0.042 / 百万 token，输出免费。已经上了 Vercel AI Gateway、OpenRouter、LiteLLM。最像
基于 Jev 的 macOS 项目（jev-cua、jev-voice 等）GitHub 上这几天冒出一批「对 Mac 说话 → Jev 选一个动作 → 用辅助功能去点」的项目，都是拿 Jev 模型做决策。不是划词工具。证明 Jev 是这周的热点
PopClip / SnipDo / Easydict / Bob发音上都和「Jev」对不上。不像
叫 Jev 的划词 / 语言检测库没有找到。不存在

结论：你说的是 TypeSafe 的 Jev 模型，把握大约八成五。理由：issue 的拼写就是「Jev」；时间对得上（发布一周，正是热点）；它的卖点——「对一段内容问一个是非题，快速拿到带把握度的答案」——正好就是你描述的「检测选中的内容是不是日文，是的话才用某个动作」。剩下那一成五的不确定是：你也可能只是在说「一个会做这种判断的东西」，而不特指这家模型。

「用 Java 定义一些判断」应该是 JavaScript，把握九成。在 Mac 上嵌一门脚本语言，JavaScript 是唯一系统自带的（JavaScriptCore），PopClip 的扩展也用它；真正的 Java 需要装 JVM，不会有人为一个判断这么做。

Jev 长什么样（官方文档，未实测）

我没有 Jev 的 API key，所以下面的格式和延迟都来自官方文档，没有在本机调用过。

// POST https://api.typesafe.ai/v1/systemone   Authorization: Bearer <key>
{
  "model": "jev-latest",
  "state": "let x = foo(bar)",              // 选中的文字
  "questions": {

}
// 返回

noul 是「是」的概率，0 到 1。官方建议 0.8 以上当「是」、0.2 以下当「否」。另有 choice（从最多 255 个选项里挑一个，附每个选项的概率）和 score（按 2–10 档打分）。

Jev 在 QDuo 里该放在哪

不要拿它判断语言。判断日文 / 英文，本地 0.02 ms、免费、不出机器；Jev 要走网络、最少 70 ms、每次选中都把文字发给第三方。

拿它做本地规则写不出来的判断：「这段是不是代码」「这是不是一个问句」「是不是一段需要润色的正式文字」「是不是商品名」。这类判断用正则写不准，用大模型又太慢太贵，正好是 Jev 的位置。

但别让它决定「按钮出不出现」。弹出条必须在约 50 ms 内出来，Jev 最快也要 70 ms，还得加网络。如果先弹出、等 Jev 答案回来再把按钮加进去，胶囊会变长、轮盘会重新分扇区——而这时你的鼠标正朝某个按钮移动。

更合适的位置是「点下去之后」：你已经点了按钮，等个两三百毫秒完全可以接受。例如一个「智能处理」分组，点它时用 Jev 的 choice 题从「翻译 / 解释代码 / 润色」里挑一个最合适的去执行。见 5.2 的流程图。

2 · 别的工具怎么做

先看同类产品给用户的「条件」长什么样。共同点很明显：几乎都有「正则 + 内容类型 + 限定 App」这三样，只有 PopClip 允许写代码，而且它对代码限制得很死。

PopClip（macOS，最接近 QDuo 的产品）

# PopClip 扩展的配置（YAML）
name: Example
requirements: [url]            # 可选值：text copy cut paste formatting url isurl urls email emails path option-xxx=yyy，前面加 ! 表示取反，如 "!url"
regex: example\.com            # 满足 requirements 之后，还要匹配这个正则才显示
requiredApps: [com.apple.Safari]   # 只在这些 App 里显示（另有 excludedApps）

PopClip 还支持 JavaScript 扩展（引擎就是 JavaScriptCore，文档写明「一个不能访问文件系统的沙盒」）。其中有个「population function」：每次弹出前都会跑一遍，返回这次要显示哪些动作——这就是「用代码决定显示什么」。但它在这个阶段明确禁止：

  • 不能联网（没有 XMLHttpRequest）；
  • 不能调 popclip 上的任何函数（只能读 input、context、options 这些属性）；
  • 不能 sleep() / setTimeout() / setInterval()；
  • 读不到标成 secret 的选项；而且必须在配置里声明 dynamic 权限。

文档没说有没有超时。这组限制很值得照抄：判断阶段只允许纯计算。

SnipDo（Windows，PopClip 的同类）

{
  "title": "My Action",
  "regex": "^https?://",                          // 文字满足正则才显示
  "requirements": ["IS_URL"],                     // 还有 HAS_URL、EMAIL、FILEPATH
  "showOnlyApps": ["chrome.exe", "firefox.exe"],
  "noShowApps": ["notepad.exe"]
}

注意它把「是网址」和「含网址」分成了 IS_URL / HAS_URL 两个——这个区分很实用，后面的设计会沿用。

Alfred Universal Actions只能勾选输入类型：Text / URLs / Files，以及「单个 / 多个」。没有正则。类型过滤是最基本、用户最容易理解的一层
Automator 快速操作 / 快捷指令「工作流程收到当前的 文本，位于 任何应用程序」——一个类型 + 一个 App。同上，外加「限定 App」

语言识别：短词到底有多不准

我挑了 30 个带标签的样本（英、日、简中、繁中、韩、法、德、西），用苹果识别器默认设置跑：25 / 30 正确。把候选语言限定为「英日简繁韩」五种后：24 / 27，错的还是那几个。错的全是这类：

apple英土耳其语tr 0.39 · en 0.15
API英印尼语id 0.27 · en 0.16
漢字日繁体中文zh-Hant 0.71 · ja 0.29

而这些都对了：ありがとう、カタカナ、東京都(ja 0.76)、新幹線(ja 0.66)、取扱説明書、会議室予約、所有中文整句、所有韩文、bonjour、Guten Morgen、gracias。

所以「是不是日文」应该这样判断
  1. 只要出现平假名或片假名 → 是日文。中文里不会出现假名。这一条把「Swift で書く」这种混排也救回来了。
  2. 没有假名、全是汉字 → 交给识别器，日语概率 ≥ 0.6 才算。
  3. 剩下的（「漢字」「寿司」这种两字词）本质上分不出来——它们在中文里也是合法的词。这是真实的上限，不是实现问题。要么接受，要么在这种情况下退回到用户的偏好（比如「我主要读日文，拿不准时当日文」）。

「是不是英文」同理：短词（apple、API）识别器会判成土耳其语、印尼语。实用的规则是「全是拉丁字母」且「识别器前三名里有英语」，比单看第一名稳得多。这两条规则都应该做成内置判断，用户只需要写 "lang": "ja"，不用自己懂这些。

4 · 让用户自己写判断：JavaScript 行不行

苹果自带 JavaScriptCore（下称 JSC），不用打包任何东西。本机实测：

操作耗时
创建第一个 JS 环境（冷启动）2.0 ms 实测
同一个虚拟机里再建一个环境0.03 ms 实测
编译一个判断函数0.2 ms 实测
调用已编译好的判断（短文字）0.0006 ms 实测
调用判断，传入 1.2 万字0.017 ms 实测
每次新建环境 + 运行0.035 ms 实测

速度完全不是问题。真正的问题只有一个：用户写了个死循环怎么办。

死循环怎么停

办法行不行代价
JSC 自带的执行时限
JSContextGroupSetExecutionTimeLimit		实测可用 设 20 ms，while(true){} 在 29 ms 被掐断；之后同一个环境、之前编译好的函数都还能正常用这是苹果未公开的接口（Safari 自己在用，符号一直在系统库里）。QDuo 走 Developer ID + 公证分发、不上 App Store，公证不查这个；风险是某天苹果改了它。用 dlsym 按名字找，找不到就关掉 JS 功能，不会崩
另开一个线程看表，超时就放弃不行公开接口里没有「从外面打断 JSC」的办法。放弃等待可以，但那个线程会一直空转吃 CPU，而且整个 JS 虚拟机被它占着

不用 JS，用 NSPredicate 表达式能用但难写实测 0.0016 ms、不会死循环。但语法是苹果那套 SELF MATCHES "…" AND length < 200，普通人不会写，报错也难懂

安全：别人分享的配置里带了 JS 怎么办

README 鼓励把 config.json 提交进公开仓库、拷到别的机器，所以要假设用户会用别人写的配置。好消息是：只要我们不往 JS 里塞任何能力，判断脚本什么坏事都做不了——JSC 本身没有文件、网络、定时器，它能做的只有「算出一个 true / false」。最坏情况是：

  • 死循环 → 执行时限掐掉；
  • 永远返回 true / false → 动作该出不出，烦人但无害；
  • 写得很慢 → 同样被时限掐掉，并在设置里标出来。

所以不需要弹窗问「是否允许脚本」。只要守住一条规矩：判断阶段只给 JS 一个只读的 sel 对象（文字、语言、来源 App……），永远不给剪贴板、网络、文件、执行动作的能力——和 PopClip 的做法一样。

建议：JS 先不做

你举的例子（日文才显示、英文才显示）都是一个内置判断就能写完的。JS 要额外付出：一个未公开接口、一套只读 sel 的约定、出错提示、文档。这些代价只有在出现「内置判断组合不出来」的真实需求时才值得。when 的格式是可以往上加叶子的，以后加 js 不影响已有配置。

另一个细节：那个时限接口的声明不在系统 SDK 的头文件里，只能自己写函数原型。如果直接链接、而某天苹果删了它，App 会在启动时就打不开；所以必须用 dlsym 在运行时按名字找，找不到就只关掉 JS 判断。

5 · 建议的设计

5.1 配置长什么样

每个动作多一个可选字段 when。没写 = 一直显示（和现在完全一样）。它是一棵小树：叶子是单个判断，all / any / not 把它们组合起来；直接写一个数组等于 all。

// ① 只在选中日文时显示
{ "title": "日译中", "kind": "ai", "prompt": "…",
  "when": { "lang": "ja" } }

// ② 只在选中英文时显示（多个语言写数组，满足任一即可）
"when": { "lang": ["en"] }

// ③ 整段就是一个网址（"is"），对比 "has"：里面含有网址
"when": { "is": "url" }
"when": { "has": "url" }          // 可选值：url email phone date address path number

// ④ 正则（默认不区分大小写可选）
"when": { "regex": "^[A-Z]{2,}-\\d+$" }       // 比如 JIRA 单号 QDUO-123

// ⑤ 组合：英文、不超过 300 字、不在终端里
"when": { "all": [
  { "lang": "en" },
  { "length": { "max": 300 } },
  { "not": { "app": ["com.apple.Terminal", "com.mitchellh.ghostty"] } }
] }

// ⑥ 任一满足：日文或韩文
"when": { "any": [ { "lang": "ja" }, { "lang": "ko" } ] }

// ⑦ 选中处带着链接（复用弹出前已经算好的链接结果）/ 选中的是一个存在的路径
"when": { "link": true }
"when": { "is": "path" }

// ⑧ 以后按需：JavaScript 表达式，sel 只读（见第 4 节，建议先不做）
"when": { "js": "sel.lines > 1 && /^\\s*[-*] /m.test(sel.text)" }

字段名选 when：VS Code 的菜单和快捷键就用这个名字表达「什么情况下生效」，写过插件的人一看就懂。showIf 太窄（以后若有「变灰」就名不副实），requirements 读起来像「安装依赖」。

叶子含义实现
lang语言，BCP-47 代码：en ja zh ko fr …；zh 同时匹配简繁，zh-Hans / zh-Hant 分开匹配第 3 节那套「假名优先 + 识别器 + 阈值」修正规则
script用到的文字：han kana hiragana katakana hangul latin，可加 "only": true 表示「只有这种字」Unicode 范围
is / has整段是 / 含有：url email phone date address path numberNSDataDetector、PathResolver、正则
regex正则；可写成 {"pattern": "...", "flags": "i"}NSRegularExpression，编译结果缓存
length / lines{"min": 1, "max": 300}计数
app来源 App 的 bundle id 列表已有
all / any / not组合短路求值：all 碰到一个 false 就停
link选中处关联着一个链接（不一定写在文字里，比如选中了超链接的文字）复用 LinkResolver 在弹出前已经算好的结果
jsJS 表达式，返回真假以后按需

老版本兼容：现在的代码已经会把不认识的字段原样保留（PopBarActionConfig.extra），所以写了 when 的配置被老版本打开时，字段不会丢，只是老版本会忽略它、照常一直显示。不需要改 schemaVersion。

5.2 一次选中之后发生什么

要点：「选中内容档案」是懒的——没有任何动作用到地址识别，就一次都不跑 NSDataDetector；语言只识别一次，十个动作都问语言也只算一次。蓝色虚线是可选的 Jev 用法：它只在点击之后发生，所以弹出条不会因为等它而晚出现或跳动。

5.3 几个规则

  • 不满足就隐藏，不是变灰。弹出条的位置很金贵；变灰的按钮还占着位置，得告诉用户「为什么灰」，在轮盘上还要保证灰扇区点不动。第一期不做「变灰」选项，以后需要再加，不影响已有配置。
  • 出错 / 超时 = 「不知道」，而「不知道」= 照常显示。判断结果有三种：是、否、不知道。不能把「不知道」简单当成「否」：{"not": {"regex": …}} 里的正则一旦超时，「否」取反就成了「是」，行为会悄悄反过来。三态一路传上去，最后只要有「不知道」就显示——动作多一个没关系，动作莫名消失才让人以为坏了。同时设置页亮黄点 + 写日志（日志里不写选中的文字）。
  • 超时要能真正甩手不管。「是不是路径」要去磁盘上查，碰上掉线的网络盘可能卡好几秒而且中途停不下来。所以求值不能「等它做完」，而是到点就不等了，结果记为「不知道」，那个卡住的查询让它在后台自己结束。
  • 双击变三击时要重新判断。现在同一处选区从一个词扩成一整行时，QDuo 只更新文字、不重建按钮（refreshTransientSelection）。有了 when 以后，文字变了按钮就可能不同，这里要重新求值。
  • 提前预热。语言识别器第一次用要 3–9 ms、NSDataDetector 第一次创建要 7 ms（实测），合起来是弹出预算的五分之一。在读完配置、发现有动作用到它们时就在后台先建好。
  • 分组：分组自己可以有 when，不满足则整组不显示；分组满足但里面的子动作一个都不满足，整组也不显示（不留空环）。胶囊模式的「把分组摊平成一排」放在过滤之后做。
  • 和已有功能的关系：「预览」「在访达中显示」现在永远出现，选中的不是路径时点下去才报错「不是本地路径」（ActionRegistry.swift 的 pathPresentation）；「网页预览」在没有链接、又关了「改为搜索」时也一样。给它们默认带上 {"is": "path"} / {"link": true}，就能把这个现有的痛点一起解决。但改默认值会改变老用户看到的东西，放到开放问题里让你定。
  • 正则防卡死：和其他判断一样放在后台线程，30 ms 等不到就记为「不知道」；卡住的那个正则在本次运行期间直接停用并标黄，免得每次选中都再卡一次。输入先截到前 4000 字。
  • 配置读取时就把 when 全部检查、编译一遍（正则、JS 函数），写错的在设置页立刻标红，而不是等到选中时才发现。

5.4 编辑界面

不建议做拖拽式的「条件搭积木」界面：工作量大，而会写组合条件的人更愿意直接写 JSON。预设下拉 + JSON 文本框 + 测试框，是投入产出最好的组合。

6 · 需要你拍板的问题

  1. Jev 指的是 TypeSafe 的 Jev 模型吗？A 是 / B 不是，是别的（请告诉我名字）。
  2. 不满足条件时：A 隐藏（推荐）/ B 变灰。
  3. 「预览」「在访达中显示」「网页预览」要不要默认只在能用时出现？A 要（新装和老用户都改）/ B 只改新装的默认 / C 不动。
  4. JavaScript 判断：A 现在就做，接受用苹果未公开的时限接口 / B 先不做，等内置判断不够用再说（推荐 B）。
  5. Jev 怎么用：A 点击后由它挑子动作（推荐，不影响弹出速度）/ B 坚持用它决定按钮显示不显示（弹出条会先少几个按钮、几百毫秒后再补上）/ C 暂不接。无论哪种，被判断的文字都会发到 TypeSafe 的服务器。
  6. 短汉字词（漢字、寿司）判不出是中文还是日文时，A 当「不满足」/ B 按你的常用语言猜。

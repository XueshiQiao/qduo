## 二、为什么会这样：根本原因

### 1. 把「评审过」当成了「验证过」

#22 的 PR 描述里写着「Reviewed in two rounds; all findings fixed」。但两轮评审都只是读代码。读代码看不出下面这些只在运行时才会出现的事：

- 有 sheet 时 `NSApp.terminate` 不退出（第 6 条）；
- zip 不保留空文件夹（第 5 条）；
- grouped Form 里的 `SecureField` 长什么样（第 2 条）；
- `TextField` 默认开着文本替换（第 9 条）。

这四个都是 AppKit 和 macOS 的行为，不是代码里写错了什么，只有真的跑起来才知道。

### 2. 成对的代码分开写，也没有测它们能不能对上

导出和导入是一对：导出写出的东西，导入必须能读进来。但当时导出（`BackupExporter`）和导入（`BackupImporter`）各自写了一遍「备份里有什么文件、manifest 怎么写」，测试也只测了零件：加密函数、zip 函数、文件名规则。

```
当时的测试：
    测 BackupCrypto.seal 和 open 能不能配对         ← 测了
    测 BackupArchive.zip 和 unzip 能不能配对         ← 测了
    测「BackupExporter 写出的 zip，BackupImporter 能不能读」  ← 没测

结果：
    零件全都对，但零件组合起来的时候，在「0 张图标」这种情况下对不上
```

### 3. 只考虑了正常情况

出问题的都是正常情况以外的情形：

- 数量是 0：0 张图标、0 条历史记录；
- 重复操作：按钮点了好几次；
- 界面状态：操作发生在 sheet 里面。

### 4. 把运行时验证整个交给了用户

PR 里写着「需要真机测试导出和导入」，于是我把真机上的所有事情都留给了用户，自己一次都没有打开过这几个窗口。这样一来，用户成了第一个看到界面、第一个点按钮的人，每个问题都要用户先发现、再告诉我。

### 5. 修 bug 时只验证一次

第 8 条：修重启的 bug 时，测试第一次碰巧通过了，我差一点就当成修好了。和时序、动画有关的问题，跑一次通过说明不了什么。

### 6. 推送前没看 PR 的状态

第 1 条：往一个 PR 分支强制推送之前，没有先查这个 PR 是不是已经合并了。

## 三、以后怎么做

下面每一条都是具体要做的动作。

### 规则 1：成对的代码放在一起，并且测往返

导出和导入、编码和解码、保存和读取，凡是「一边写、一边读」的代码：

```
把「格式」写在一个地方（例如 BackupLayout、BackupKeysFile），写的一边和读的一边都调用它
写往返测试：用写的一边生成，经过真实的容器（真的 zip、真的文件），再用读的一边读回来
往返测试必须覆盖：
    每一种可以勾选的组合
    数量为 0 的情况（0 张图标、0 条记录、空字典）
    读的一边应该拒绝的情况（密码错、文件被改过、缺文件）
做一次变异检查：故意把代码改坏，确认测试会失败，再改回来
```

现在 #22 已经这样做了：`BackupLayout` 和 `BackupKeysFile` 是导出、导入共用的代码；`BackupLayoutRoundTripTests` 跑了 15 种组合和 0 张图标的情况；导出完成以后，还会先按导入的方式把 zip 读一遍（`BackupLayout.verify`），读不通就不交给用户。

### 规则 2：能自动测的，不让人测

给用户列测试清单之前，逐条问一句：这一项能不能用单元测试或者脚本测？

```
对 测试清单里的每一项：
    如果 是纯逻辑（加密、格式、计算、往返）：写单元测试，不放进清单
    否则如果 是 AppKit 运行时的行为（退出、重启、sheet、焦点）：写一个最小的测试程序，在真实的场景里跑
    否则（界面看起来怎么样、真实的钥匙串、真机权限）：才放进让用户测的清单
```

### 规则 3：新界面自己先看一眼

新做的窗口、sheet、表单，交给用户之前，自己先把它打开看一遍，截一张图：在测试程序里把这个视图画出来（`NSHostingView` 加 `screencapture`，或者 `ImageRenderer`）。要看的是：输入框看不看得出来、勾选框有没有对齐、按钮灰着的时候有没有说明原因。

### 规则 4：AppKit 生命周期的操作要有测试脚本，并且要防重复

退出、重启、弹模态窗口这类操作：

- 在真实的场景里测。比如「Restart Now」在 sheet 里，测试程序里就要挂一个 sheet。
- 测「点好几次」的情况。
- 和时序有关的测试，至少连续跑 5 次。
- 有副作用的事情（启动另一个进程、写文件），要放在「确定会发生」以后再做。比如重启用的脚本，现在改为在 `willTerminate` 里才启动。

这一类的测试脚本放在 `scripts/` 里，例如 `scripts/check-relaunch.sh`：在挂着 sheet 的情况下请求重启三次，检查旧进程退出了，并且只开了一个新进程。改 `AppRelaunch.swift` 以后要跑一次。

### 规则 5：评审不能代替运行

评审（Alice、Frank）查的是代码逻辑。汇报「做完了」的时候，要分开写：哪些是跑过验证的（单元测试、脚本、真机），哪些只是读代码看过。PR 描述里不能只写「评审过」。

### 规则 6：输入密码的地方，用户看到的就是存下的

- 密码框显示明文，用等宽字体。
- 关掉所有会改动输入的功能：文本替换、智能引号、破折号、拼写更正、粘贴时自动加空格（`PasswordField.typeAsIs`）。
- 只有空格不算设了密码。

### 规则 7：往 PR 分支推送之前，先看 PR 的状态

```
往一个开着 PR 的分支推送之前：
    运行 gh pr view <编号> --json state,mergedAt
    如果 PR 已经合并：不要推送到这个分支，从最新的 main 拉新分支，另开一个 PR
合并之后：
    比较 main 的内容和测过的那份提交是否完全一样（git rev-parse <提交>^{tree}）
```

### 规则 8：拿用户的真实数据做测试之前，先留后路

要删除或者覆盖用户的数据来测试时，先把数据挪到一个文件夹里，不要直接删。恢复的时候用复制，不要用移动，这样再出问题还能再恢复一次。这次就是这么做的：`~/qduo-removed-for-backup-test-20261023-220211/`。
